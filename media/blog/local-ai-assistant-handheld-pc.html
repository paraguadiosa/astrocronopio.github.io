I built a local AI assistant on a handheld PC — then I moved it to an API

Aug 2026 · LLM serving, hardware

I built my own local AI assistant, a full agent, with a Discord frontend, a systemd service, and a personality of "Moria Casán impersonating a supercomputer." I ran it on a Win Mini 2025: an AMD Ryzen AI 9 with a Radeon 890M integrated GPU and 64GB of unified memory, running Nobara Linux. I got it to 17 tokens per second with a 9B model, 4 t/s with a 27 B model - happy with experiment but I ended up using the Deepseek API

Why local at all

I work in MLOps and I was curious on how inference works, and stop treating inference as a black box that somebody else runs. I wanted to know what a infering the token actually costs on hardware I can touch. The only way to learn that is to serve a model yourself and fix things until it works.

The hardware reality

The Win Mini is a beautiful little machine - I called it jokingly My Husband - a whole computer in your palm with 64GB of unified memory. But the GPU is integrated: its "VRAM" is just a slice of system RAM, and every access competes with the CPU. No amount of stubborness makes a handheld PC compete with paying an API but I had fun and I learned.

The setup

Install ROCm on Nobara, add your user to the render and video groups, and check your GPU target: 

sudo dnf install rocm-hip rocm-opencl rocminfo
sudo usermod -aG render,video $USER
rocminfo | grep gfx        # -> gfx1150 on the Ryzen AI 9

Compile llama.cpp against ROCm. The flag that matters is GGML_HIP: 

cmake -B build -DGGML_HIP=ON -DAMDGPU_TARGETS=gfx1150 -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j$(nproc)

Download a GGUF with the Hugging Face CLI and serve it with all layers offloaded: 

hf download <org>/<model>-GGUF <file>.gguf --local-dir ./models
./build/bin/llama-server -m ./models/<file>.gguf -ngl 999 -c 8192 \
  --host 0.0.0.0 --port 8080

The wins

Two things made the difference:

First, an MTP draft head (multi-token prediction), the model drafts several tokens and verifies them in parallel, so the GPU stays busy instead of stalling on one token at a time. That took me from a frustrating session at 4 t/s to a measured 9.0 t/s on a Qwythos-9B Q6_K. Nine tokens per second is not fast, but it is readable, and for an async Discord bot that lives in a systemd service, readable is enough.

Second, the BIOS UMA trick. On integrated GPUs, the amount of RAM the GPU gets to use is configured in BIOS — AMD CBS → UMA Frame Buffer Size. Setting it to 32GB gives the GPU a dedicated chunk instead of fighting the CPU for every access. I measured 17.0 t/s on a Qwythos-9B Q6_K, i was very happy with that

The honest truth

Here is the part I did not want to admit for a while: 17 t/s is fine for a bot that answers when it feels like it but terrible for my workflow. I work in long sessions. a context that grows to tens of thousands of tokens, iterative edits, questions that need the model to have read the whole repo. At 17 t/s with 70k of context, every turn costs minutes, the fans spin up and I start optimising my questions instead of my code.

And there is the maintenance tax. A local stack is a service you are on call for: BIOS settings, ROCm updates that break your build, quantization choices, the 2am out of memory because the context window grew and the UMA died. My day job is literally keeping ML systems reliable in production, IT PAINS ME to build my own unreliable production system.

Why I moved to DeepSeek V4 Flash

DeepSeek V4 Flash via API gives me answers in seconds instead of minutes, quality at or above what the local 9B could do, zero hardware babysitting, and a cost per token that is frankly trivial compared with my time. The tradeoff is that my prompts leave my house for the workloads that need it, still work with a mix of local/API setup.

From inference setup to Lab setup

The Win Mini did not get retired, it went from "production assistant" to "lab": finetuning experiments with unsloth, axolotl on ROCm and model evaluation, that's where a my little machine is fine and privacy is a feature - hopefully next blog.

I am glad I built it. I know what a token costs now, in a way that reading a blog post would never have taught me. And knowing that is exactly why I stopped serving locally: the practical choice was the API, and the practical choice is the reliable one.
