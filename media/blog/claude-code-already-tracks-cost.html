Claude Code already tracks its cost. I wanted to see it.

Aug 2026 · LLM telemetry, observability, Prometheus, OpenTelemetry

In the previous post I built the entire pipeline by hand: five agents, five storage formats, one adapter per agent, a dedup wrapper, a Pushgateway, Grafana. At home nothing emitted metrics, so I built everything.

At work it happened the other way around. The telemetry already existed. Claude Code ships native OpenTelemetry metrics (cost, tokens, model, per user) straight to the staging Pushgateway.

The problem: real money, invisible bill

The org spends real money on AI coding tools and almost nobody can see the invoice. The Anthropic Admin Console is reachable by a handful of people (CTO, and so on).

A question nobody could answer: how much do we spend, per model, per team, and is it worth it?

The original plan was a parser for the JSONL files in ~/.claude/projects. My own rule: metadata only, never prompt content.

The accident: a smoke test found the emitter already existed

Smoke test on staging: a manual push under the job claude_code_eve_smoketest to the preview Pushgateway. Instead of my homegrown metrics, the NATIVE Claude Code ones appeared (otel_scope com.anthropic.claude_code, v2.1.235). The curl that revealed everything: 

curl -s http://pushgateway-preview.<company>.com/metrics \
  | grep -A2 'job="claude_code_eve_smoketest"' | grep cost_usage_total | head -5
claude_code_cost_usage_total{instance="<work-machine>",job="claude_code_eve_smoketest",model="claude-haiku-4-5-20251001",otel_scope_name="com.anthropic.claude_code",otel_scope_version="2.1.235",query_source="auxiliary",session_id="9699d657-...",user_email="eve@<company>.com"} 0.001251

Rich labels out of the box: user_email, user_id, model, query_source (main vs auxiliary: the agent overhead costs almost as much as the main answer), effort, session_id, terminal_type, organization_id.

The emitter already exists and it is Anthropic's: zero instrumentation, zero code to maintain. The work became configuring the export, a dashboard, and onboarding.

The trap: "telemetry on" but Prometheus read it wrong

claude_code_cost_usage_total is a COUNTER. Counters reset: new process, restart, re-emission.

The naive panel query was sum(claude_code_cost_usage_total). When the counter resets, the sum() loses everything the reset ate, under-reporting cost by 90% or more.

The personal smoke test caught a REAL defect before rollout. That is exactly what a staging pilot is for. 

# WRONG: sum() on a resetting counter under-reports cost by 90%+
sum(claude_code_cost_usage_total)

# RIGHT: increase() handles counter resets
sum(increase(claude_code_cost_usage_total[$__range]))

The mirror with home (previous post): the same Prometheus lies in both directions depending on the metric type. At home the wrapper pushes a cumulative gauge (totals) and increase() INVENTED money when a push corrected values (the x10 spike day, a phantom $1,252). Here the native counter makes sum() LOSE money.

Lesson: the correct query depends on the metric type, not on what sounds right.

Staging as a lab

pushgateway-preview.<company>.com: test the full pipeline without touching prod. The dashboard "Claude Code - Usage & Cost" on staging Grafana came alive with real smoke test data.

Verified numbers (last 3h): $3.92, 5.63M tokens, 9.8 min active. Split by model (claude-sonnet-5, claude-haiku-4-5-20251001) and by query_source (main vs auxiliary).

Lessons

  • The factory emitter kills the zero code to maintain parser. If the tool already emits OTel, do not maintain a parser that breaks with every update. The work is reading well, not instrumenting.
  • The metric type defines the query. Counter → increase()/rate(). Cumulative gauge → delta with clamp. Mixing them = money that does not exist or money that disappears.
  • Staging is where bugs die. The smoke test caught the counter-reset before an org dashboard showed 10% of the real spend.
  • The data was already there. Visibility is not building telemetry, it is daring to look at what your tools already emit.

The phrase from the previous post, on a different field: "Measurement is the reliable choice." At home I built it. At work I just had to read it correctly.
